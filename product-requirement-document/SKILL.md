# 产品需求文档（PRD）撰写

## 触发条件

当用户表达以下意图时自动应用此 skill：
- "写 PRD"
- "产品需求文档"
- "出需求"
- "需求分析"
- "功能规格说明"
- "帮我整理需求"

## 工作流程

### 第一步：信息收集

在开始撰写前，向用户收集以下信息：

**必需信息：**
- [ ] 需求名称/标题
- [ ] 产品经理姓名（用于修订记录和分工）
- [ ] 需求背景（产品经理的原始描述）
- [ ] 需求内容/功能描述

**文档命名规则：**

PRD 文档标题必须遵循以下命名格式：

```
【需求状态】作者姓名-YYYYMMDD-需求名称
```

**命名示例：**
- 【PRD】陈志明-20260403-中心仓配送费发票类别调整
- 【PRD】张三-20260403-优惠券功能

**规则说明：**
- **需求状态**：初始状态固定为 `【PRD】`
- **作者姓名**：产品经理姓名
- **YYYYMMDD**：当前日期，格式如 `20260403`
- **需求名称**：简洁描述需求内容

**生成文档标题时：**
1. 自动获取当前日期格式化为 YYYYMMDD
2. 使用产品经理姓名作为作者
3. 使用用户提供的需求名称
4. 组合成完整标题：`【PRD】{姓名}-{日期}-{需求名称}`

**可选信息：**
- [ ] 需求优先级（P0/P1/P2）
- [ ] 涉及的系统/模块
- [ ] 是否需要绘制流程图/架构图
- [ ] 是否涉及小程序/APP（需要数据埋点）
- [ ] 产品需求池链接
- [ ] 设计稿链接

### 第二步：PRD 结构生成

按照以下结构生成 PRD 文档：

#### 1. 修订记录

| 版本号 | 修订日期 | 修订内容 | 修订者 |
|--------|----------|----------|--------|
| V1.0 | YYYY-MM-DD | 初稿 | {产品经理姓名} |

**规则：**
- 初始版本号固定为 V1.0
- 日期自动获取系统当前时间，格式：YYYY-MM-DD
- 初稿版本的修订内容为"初稿"
- 修订者为产品经理姓名

#### 2. 相关链接

| 事项 | 内容 |
|------|------|
| 产品需求池 | {用户提供的链接或"待补充"} |
| 设计稿 | {用户提供的链接或"待补充"} |

**规则：**
- 固定包含"产品需求池"和"设计稿"两行
- 表格为两列结构：事项、内容
- 如用户未提供，填写"待补充"

#### 3. 需求概述

**要求：**
- 基于产品经理的原始描述进行分析和润色
- 用专业的产品语言重新组织
- 突出核心价值和用户痛点
- 控制在 200-300 字

**结构：**
```
【背景】
{润色后的需求背景}

【核心需求】
{提炼后的功能需求描述}

【预期效果】
{简述预期达成的业务目标}
```

#### 4. 需求背景与目标

**背景（润色版）：**
- 将产品经理的口语化表述转化为专业文档语言
- 说明当前存在的问题/痛点
- 阐述为什么要做这个功能

**目标：**
- 根据需求背景和内容推导具体目标
- 使用 SMART 原则（具体、可衡量、可达成、相关、有时限）
- 分点列出 2-4 个核心目标

**示例：**
```markdown
### 背景
当前用户在下单流程中，无法实时查看物流状态，需要跳转到第三方平台查询，体验较差...

### 目标
1. 在订单详情页集成物流追踪功能，减少用户操作步骤
2. 支持主流物流公司的实时查询，覆盖 95% 以上的订单
3. 物流状态更新延迟控制在 5 分钟以内
```

#### 5. 需求范围与分工

**需求范围：**

根据需求内容圈定改动的系统和功能模块：

| 系统/模块 | 功能描述 | 优先级 |
|-----------|----------|--------|
| {模块1} | {功能描述} | P0 |
| {模块2} | {功能描述} | P1 |

**需求分工：**

| 角色 | 负责人 | 职责 |
|------|--------|------|
| 产品经理 | {产品经理姓名} | 需求定义、验收标准制定 |
| UI设计师 | 待分配 | 界面设计、交互设计 |
| 前端开发 | 待分配 | 页面实现、交互逻辑 |
| 后端开发 | 待分配 | 接口开发、数据处理 |
| 测试工程师 | 待分配 | 测试用例编写、功能测试 |

#### 6. 业务逻辑（可选）

**判断条件：**
- 如果需求涉及复杂业务流程，需要绘制流程图
- 如果涉及系统架构调整，需要绘制架构图
- 如果产品经理明确需要可视化流程说明

**处理方式：**
- 使用 `ai-draw` skill 绘制流程图或架构图
- 在文档中插入图表，并配合文字说明
- 图表需包含：流程节点、判断条件、数据流向

#### 7. 功能详细说明

**结构要求：**

按照需求范围中的模块拆分，每个功能模块单独说明：

```markdown
### 7.1 {功能模块名称}

**功能定位：**
{简述该功能在整体需求中的作用和定位}

**产品规则：**
1. {规则1}
2. {规则2}
3. {规则3}

**字段定义：**

| 字段名 | 字段类型 | 是否必填 | 说明 |
|--------|----------|----------|------|
| {字段1} | string | 是 | {说明} |
| {字段2} | number | 否 | {说明} |

**业务定义：**
- {业务逻辑说明1}
- {业务逻辑说明2}

**交互说明：**
- {交互细节1}
- {交互细节2}

**异常处理：**
- {异常情况1}：{处理方式}
- {异常情况2}：{处理方式}
```

**注意：**
- 每个功能模块都必须包含"功能定位"说明
- 字段定义表格必须包含：字段名、字段类型、是否必填、说明
- 异常处理要覆盖主要异常情况

#### 8. 数据埋点（如涉及小程序/APP）

**判断条件：**
- 需求涉及小程序前端 → 需要埋点
- 需求涉及 APP 前端 → 需要埋点
- 纯后端需求 → 可省略此章节

**埋点表格结构：**

| 埋点功能 | 埋点页面 | 埋点事件 | 终端 |
|----------|----------|----------|------|
| {功能描述} | {页面路径} | {事件名称} | 小程序/APP/H5 |
| 例：页面浏览 | /pages/order/detail | page_view | 小程序 |
| 例：按钮点击 | /pages/order/detail | btn_click_express | 小程序 |

**埋点事件命名规范：**
- 页面浏览：page_view
- 按钮点击：btn_click_{按钮标识}
- 表单提交：form_submit_{表单标识}
- 列表曝光：list_expose_{列表标识}

#### 9. 其他补充说明

**用途：**
- 附录文件引用
- 需求进度更新
- 业务规则映射表
- 特殊说明事项

**格式：**
```markdown
### 附录
- {附录1名称}：{说明或链接}

### 进度更新
- YYYY-MM-DD：{更新内容}

### 特殊说明
{需要特别说明的内容}
```

## 质量检查清单

### 第三步：文档标题生成

根据命名规则生成文档标题：

```python
title = f"【PRD】{产品经理姓名}-{当前日期YYYYMMDD}-{需求名称}"
```

**示例：**
- 输入：需求名称="优惠券功能", 产品经理="陈志明", 日期="2026-04-03"
- 输出：`【PRD】陈志明-20260403-优惠券功能`

## 质量检查清单

生成 PRD 后，检查以下项目：

- [ ] 修订记录包含 V1.0、当前日期、"初稿"、产品经理姓名
- [ ] 相关链接表格包含产品需求池和设计稿两行
- [ ] 需求概述已润色，非原始口语表述
- [ ] 需求背景与目标逻辑自洽
- [ ] 需求范围列出了所有改动的系统/模块
- [ ] 每个功能模块都有功能定位说明
- [ ] 字段定义表格格式正确
- [ ] 如涉及前端，包含数据埋点章节
- [ ] 文档整体语言专业、逻辑清晰
- [ ] 文档标题符合命名格式：`【PRD】{姓名}-{YYYYMMDD}-{需求名称}`

## 注意事项

1. **语言风格**：使用专业产品语言，避免口语化表达
2. **逻辑完整**：确保背景→目标→范围→功能说明逻辑连贯
3. **可执行性**：功能说明要具体到开发可执行的程度
4. **一致性**：同一文档中术语、格式保持一致
5. **可维护性**：预留修订记录空间，方便后续迭代
